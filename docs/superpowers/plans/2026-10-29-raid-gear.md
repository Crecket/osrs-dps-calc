# Raid Gear Planner (POC) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `/raid` page that, for a raid route, a GP budget and owned/excluded items, assembles a worn setup + inventory switches with the lowest total solo kill time and shows it as in-game equipment and inventory grids plus GearScape-style per-boss DPS rows.

**Architecture:** Raids are data (`src/raid/raids/*`): stops → boss options → phases (monster id + version, default defence reductions, rules). Candidates come from the existing best setup search (`runBestSetup`, `src/best/lib/run.ts`) run per route phase at a few price tiers (items above the tier and not owned are excluded). A pure greedy assembler (`src/raid/lib/assemble.ts`) picks candidate setups into a loadout within budget and slots; a pure layout function places it into worn slots and a 28-slot inventory. A MobX store saves inputs; the search runs only from a button.

**Tech Stack:** Next.js 13 / React 18, MobX, TypeScript, Tailwind, Jest (`yarn jest src/tests/raid --coverage=false`), localforage, OSRS Wiki prices API.

**Spec:** `docs/superpowers/specs/2026-10-29-raid-gear-design.md`

## Global Constraints

- No changes to the calc engine (`src/lib/**`). Raid code lives in `src/raid/**`; the only edits outside it are the spellbook filter in `src/best/types.ts` + `src/best/lib/run.ts`, the nav link in `src/bulk/components/BulkNavLink.tsx`, and the new route `src/app/raid/page.tsx`.
- Nothing Fractured Archive–specific outside `src/raid/raids/fracturedArchive.ts`.
- The search starts only from a "Find raid gear" button; input changes mark results stale, never auto-run.
- Prices: `https://prices.runescape.wiki/api/v1/osrs/mapping` and `https://prices.runescape.wiki/api/v1/osrs/latest`, cached in localStorage for 1 hour (every read/write in try/catch).
- Owned items cost 0. Items without a price (untradeable) cost 0.
- Thralls: flat `THRALL_DPS = 0.625` added to every phase's DPS, only with the Thralls magic option.
- Commit messages: one short line, no body, no attribution lines.

## Review Focus

- Budget smaller than the required items (Venator bow for Moia, defence weapons): show "over budget" with the required items still placed, not a crash or an empty page. → Task 6 test `required items are kept even over budget`.
- A required item that is excluded (Venator bow excluded, Elder maul excluded): rule drops / counter treated as 0, with a note. → Task 1 test `excluded weapon zeroes its defence reduction`, Task 7 test `required items`.
- Dagon'hai on the route with Thralls or Ancients and the rule on: the run button is disabled with a reason. → Task 7 test `blocks thralls through Dagon'hai`.
- Price fetch fails or is blocked (offline, CORS): the page still runs with every item priced 0 and says prices are unavailable. → Task 2 test `fetch failure gives null and keeps cached prices`.
- Too many switches for the free inventory slots: layout reports the overflow count instead of dropping items silently. → Task 5 test `reports overflow`.

### Task 6: Loadout assembly (greedy, restarts, swaps)

**Files:**
- Create: `src/raid/lib/assemble.ts`
- Test: `src/tests/raid/assemble.test.ts`

**Interfaces:**
- Consumes: `Candidate` (Task 4), `freeSwitchSlots` (Task 5).
- Produces:
  ```ts
  export const THRALL_DPS = 0.625;
  export const NO_SETUP_SECONDS = 600;
  export interface AssembleInput { phases: { key: string; hp: number }[]; candidates: Candidate[]; priceOf: (id: number) => number; budget: number; requiredIds: number[]; maxItems: number; extraDps: number }
  export interface PhasePick { key: string; candidate: Candidate | null; seconds: number }
  export interface RaidPlan { itemIds: number[]; cost: number; totalSeconds: number; picks: PhasePick[]; overBudget: boolean; main: Candidate | null }
  export const assembleLoadout = (input: AssembleInput): RaidPlan;
  ```
- Algorithm (the part the signature doesn't fix):
  - `seconds(L)` per phase = `hp / (best candidate dps with every itemId in L + extraDps)`, or `NO_SETUP_SECONDS` when none fits (with `extraDps` alone if > 0: `hp / extraDps` capped at `NO_SETUP_SECONDS`).
  - Start `L = requiredIds`. Run two greedy passes from that start and keep the one with the lower total (ties: lower cost): pass A scores a step by `gain / (Δcost + 100_000)`, pass B by `gain`. A step = adding one candidate's missing items; allowed when `cost(L') <= budget` and `|L'| <= maxItems`; taken only with `gain > 1e-6`. Stop when no step is allowed.
  - **Force/ban starts for the big items** (guards against one huge item eating the budget, and values each item over the whole raid): take the `KEY_ITEMS = 5` most expensive non-required, non-free items that appear in any candidate. For each, run both passes once with the item **forced** (start `L = requiredIds ∪ {item}`) and once with it **banned** (candidates containing it are skipped). With the base run that's 11 starts × 2 passes. Keep the plan with the lowest total (ties: lower cost).
  - **Swap polish** on the kept plan: for each picked candidate, remove the items only it uses (not required, not used by another pick), then refill greedily with pass A; keep the change if the total drops. Repeat until a full sweep changes nothing (cap 5 sweeps).
  - **Speed:** give each distinct item an index and store each candidate's items as a bitmask (`Uint32Array` words), so "fits in L" is a word-wise AND; keep each phase's candidates sorted by DPS so its best usable one is the first that fits; after a step re-time only the phases whose candidates use an added item. No DPS is recalculated.
  - Export `KEY_ITEMS`.
  - `main` = the picked candidate whose phases add up to the most seconds. `overBudget` = `cost(requiredIds) > budget`.
  - `maxItems` = `11 + freeSwitchSlots(...)` — the caller computes it (Task 7).

- [ ] **Step 1: Write the failing tests** with hand-made candidates (item ids 1..n, prices via a map):
  - `owned items are free`: a 3b candidate whose items are priced 0 is picked with budget 0.
  - `spends where it saves most time`: budget 4b; candidate X (one 3.2b item) saves 10 s on one phase, candidates Y + Z (1b + 2b) save 30 s on two phases → plan contains Y and Z, not X.
  - `maxes out with a huge budget`: budget 20e9 → every phase uses its fastest candidate, cost < budget.
  - `required items are kept even over budget`: required item priced 5b, budget 1b → `itemIds` includes it, `overBudget === true`.
  - `thralls add flat dps`: one phase hp 600, no candidates, `extraDps 0.625` → seconds 600 (capped); with a 6 DPS candidate → 600 / 6.625.
  - `respects maxItems`: two candidates of 3 items each, `maxItems 4` → only one is added.
  - `second best beats one huge item`: 5 phases; item H (3.2b) gives the best DPS on all 5 and is what both greedy passes take first; cheaper items A..E (0.15b each) are each slightly worse on one phase; budget 3.5b leaves room for only H + 2 of them.   - `item that helps many bosses beats a per-boss favourite`: item S (1b) is second-best on 4 phases; item T (1b) is best on 1 phase only; budget 1b → plan holds S (forced-S start), not T.
  - `swap polish frees a slot`: a plan where an early pick is fully covered by later picks ends without it (its items not in `itemIds`).
  - `stays fast`: 300 random candidates over 9 phases with 40 distinct items finish in < 1000 ms.
