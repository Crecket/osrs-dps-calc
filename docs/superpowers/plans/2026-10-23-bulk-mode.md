# Bulk Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `/bulk` page to the OSRS Wiki DPS calculator fork that runs saved presets (many setups × many monsters) across a web-worker pool and shows a sortable table with gear icons in a row and a spec mode, hosted on Cloudflare at `bulk-dps-calc.olm.pet`.

**Architecture:** All new code lives under `src/bulk/` plus the route `src/app/bulk/page.tsx`. Two adapter files are the only bulk code that imports upstream internals: `src/bulk/lib/compute.ts` (worker-safe; `src/lib/**` only) and `src/bulk/lib/presetIO.ts` (main thread; reuses upstream's import migrations by driving a scratch `GlobalState`). A dedicated worker pool (`src/bulk/worker/`) fans jobs out; pure table logic (`src/bulk/lib/table.ts`) handles filtering and sorting; a small MobX `BulkStore` persists presets to localforage key `dps-bulk-presets`.

**Tech Stack:** Next.js 14 (static export), React 18, MobX 6, Tailwind, Jest 29 + ts-jest (jsdom), Yarn 4, Wrangler (Cloudflare Workers static assets).

**Spec:** `docs/superpowers/specs/2026-10-23-bulk-mode-design.md`

## Global Constraints

- Do not edit `src/lib/**`, `src/worker/**`, `src/state.tsx`, `src/types/**`, `src/utils.ts`, or upstream env files. The only upstream file touched is `src/app/components/TopBar.tsx` (one link), plus `package.json` scripts/devDependencies and `.gitignore`.
- Never read or write localforage keys `dps-calc-prefs`; `dps-calc-state` is read-only for bulk. Bulk's own key is `dps-bulk-presets`.
- Bulk results must equal what `PlayerVsNPCCalc` gives for the same prepared player and monster (parity).
- Worker messages are JSON strings using `WORKER_JSON_REPLACER` / `WORKER_JSON_REVIVER` from `src/utils.ts`.
- Gear slot order, exactly: `head, cape, neck, ammo, weapon, shield, body, legs, hands, feet, ring`.
- Default sort: normal mode `dps` descending; spec mode `specExpected` descending.
- Spec mode hides rows whose spec is `null` (no supported spec); `PARTIALLY_IMPLEMENTED` specs stay with a warning.
- Worker count: `Math.max(1, (navigator.hardwareConcurrency || 2) - 1)`.
- Hosting: domain root (empty `NEXT_PUBLIC_BASE_PATH`), `NEXT_PUBLIC_BASE_URL=https://bulk-dps-calc.olm.pet`, `NEXT_PUBLIC_SHORTLINK_URL=https://dps.osrs.wiki`.
- Match upstream style: 2-space indent, single quotes, airbnb ESLint config (`yarn lint` must pass), Tailwind classes and dark theme used elsewhere.
- Work on a local git branch `bulk-mode`; commit per task; never push.

## Review Focus

1. A preset with zero setups or zero monsters → Run button disabled with a one-line reason; no workers spawned.
2. Spec mode when no setup has a supported spec → an empty-state message ("No setups in this preset have a supported special attack"), not a blank table.
3. A calc that throws for one setup × monster pair → that row shows an error marker and sorts to the bottom; every other row still completes.
4. A saved item ID that no longer exists after an upstream data update → the item is dropped, the preset still loads, and a warning names the setup.
5. Re-running (or switching presets) mid-run → rows from the old run never appear in the new table.

Each is pinned by a test in the owning task (Tasks 2, 3, 4, 5).

### Task 5: Worker pool

**Files:**
- Create: `src/bulk/worker/protocol.ts`, `src/bulk/worker/bulkWorker.ts`, `src/bulk/worker/BulkPool.ts`
- Test: `src/tests/bulk/BulkPool.test.ts`

**Interfaces:**
- Consumes: `computeRow` (Task 2).
- Produces:
  - `protocol.ts`: `interface BulkChunkRequest { runId: number; chunkId: number; setups: BulkSetup[]; monsters: BulkMonster[]; jobs: [number, number][] }` (setup index, monster index); `interface BulkChunkResponse { runId: number; chunkId: number; rows: BulkRow[] }`; `handleChunk(req: BulkChunkRequest): BulkChunkResponse` (pure; calls `computeRow` per job).
  - `bulkWorker.ts`: `self.onmessage` → parse with reviver → `handleChunk` → `postMessage(JSON.stringify(res, WORKER_JSON_REPLACER))`.
  - `BulkPool.ts`: `export interface WorkerLike { postMessage(m: string): void; onmessage: ((e: { data: string }) => void) | null; terminate(): void }`; `export class BulkPool { constructor(opts?: { size?: number; createWorker?: () => WorkerLike; chunkSize?: number }) ; run(setups: BulkSetup[], monsters: BulkMonster[], onProgress: (p: { rows: BulkRow[]; done: number; total: number }) => void): Promise<BulkRow[]>; cancel(): void; shutdown(): void }`. Defaults: size per Global Constraints, `chunkSize` 25, `createWorker` = `new Worker(new URL('./bulkWorker.ts', import.meta.url))`. Workers spawned lazily on first `run`. Jobs ordered setup-major. Starting a new `run` cancels the previous one: its promise rejects with `Error('cancelled')` and responses with an old `runId` are ignored. `onProgress.rows` is the cumulative list.
